Gramaire's whole idea is in its name — _gram + mark_, grammar plus Markdown. A
`.gram.md` file is a normal Markdown document that renders on GitHub — prose,
railroad diagrams, FIRST/FOLLOW tables — and is **at the same time** the exact
input the parser generator reads. Your grammar _is_ your documentation.

This tutorial builds a small calculator grammar in two passes: **Part 1** writes
a <Term name="recognizer">recognizer</Term> that decides whether input is valid,
and **Part 2** attaches _actions_ that turn a valid parse into a value. The `gramaire` CLI and the
[Lab](/gramaire/lab) run the **same** PureScript core — the Lab is that core
compiled to WebAssembly-class browser ESM — so a verdict in the browser matches
the CLI.

<Aside type="tip" title="The Lab runs the real engine">
  The browser Lab is not a stub: it bundles the compiled Gramaire core and lexes
  input from a grammar's literal terminals **and** its token classes (ALL-CAPS
  names like `NUMBER`, declared as `NUMBER : /[0-9]+/`), then parses with the LR
  tables — entirely client-side, with no server round-trip. Your grammar never
  leaves the page.
</Aside>

## 1. The shape of a `.gram.md` file

A grammar file is a canonical Markdown document with a fixed structure:

<Steps>

1. **One `# H1`** — the grammar's name.

2. **One `## H2` per nonterminal** — the heading names the rule; a `gramaire`
   fenced block under it holds its productions.

3. **Reserved `## H2` sections** — `Precedence`, `Error messages`, and
   `Generated tables`, in that order, when present.

4. **Everything else is prose** — paragraphs, images, and `###`+ headings are
   free presentational grouping the compiler ignores.

</Steps>

One file is exactly one grammar: one start symbol, one namespace. Productions
live in fenced blocks whose info string is `gramaire`; everything outside them is
documentation that travels with the grammar.

## 2. Your first rule

Create `calc.gram.md` and give it a title and a first nonterminal:

````md
# Calc

A small arithmetic grammar.

## Expr

An expression is a sum or difference of terms.

```gramaire
Expr
  : Expr '+' Term
  | Expr '-' Term
  | Term
```
````

Reading the `gramaire` block:

- `Expr` on its own line names the nonterminal; the `:` on the next line begins
  its alternatives.
- `|` separates alternatives — and it is the **only** separator. A line break
  inside an alternative is insignificant, so a long alternative may wrap freely.
- Quoted spellings like `'+'` (single or double quotes) are **literal
  terminals** — the exact text to match.
- A **mixed-case** name (`Expr`, `Term`) is a nonterminal; an **ALL-CAPS** name
  (`NUMBER`) is a lexer token class. A mixed-case name you never define is a
  missing rule — Gramaire rejects it by name rather than treating it as a phantom
  terminal.

<Aside type="caution" title="Heads vs. fields">
  A rule head is `Name` on its own line, then `:` on the next — the line break
  is load-bearing. It is the one thing that distinguishes a head from a
  `name:Sym` **field** (written `IDENT : Sym` with no break, see §4). So never
  write a head inline as `Name : …`.
</Aside>

Add the remaining rules — `Term`, then `Factor` for numbers and parentheses:

```gramaire
Term
  : Term '*' Factor
  | Term '/' Factor
  | Factor

Factor
  : '(' Expr ')'
  | NUMBER
```

`Factor` mentions the `NUMBER` token class but nothing has said what a `NUMBER`
_is_ yet. Declare token classes in a reserved `## Tokens` section, each an
ALL-CAPS name bound to a `/regex/`; mark throwaway classes (whitespace) `%skip`:

````md
## Tokens

```gramaire tokens
NUMBER : /[0-9]+/
WS     : /[ \t\r\n]+/   %skip
```
````

That is the whole recognizer's vocabulary. Gramaire renders each rule as a
**railroad diagram** — the same SVGs `gramaire fmt` writes back into your
`.gram.md`, so the committed file documents itself. Here is the calculator's
shape, the stratification visible at a glance:

## 3. Surface sugar

Writing pure, left-recursive, epsilon-free productions by hand is wordy.
Gramaire gives you sugar that compiles down to that clean core automatically
(`Gramaire.Desugar`), so the table generator never sees a nullable rule.

<CardGrid>
  <Card title="Repetition">
    `X+` one-or-more, `X*` zero-or-more, `X?` optional. `X+` becomes a fresh
    left-recursive list; `X*` and `X?` enumerate present/absent at the use site,
    so the core stays epsilon-free.
  </Card>
  <Card title="Separated lists">
    `Comma<X>` and `Sep<X, S>` expand to one-or-more lists separated by `,` or by
    any symbol `S` — e.g. `'{' Comma<Member> '}'`.
  </Card>
  <Card title="Named fields">
    `left:Expr` names a right-hand position. The name rides onto the IR
    (`rhs[].field`) and drives generated CST accessors and visitors — without
    changing the recognized language.
  </Card>
  <Card title="Inline folding">
    `#[inline]` on a rule folds its single production into every use site, then
    drops it — a DRY tool, and a way to hand-fit a grammar into LR(1).
  </Card>
</CardGrid>

For example, a statement block is just:

```gramaire
Block
  : '{' Sep<Stmt, ';'> '}'
```

## 4. Precedence and conflicts

A <Term name="shift-reduce">shift/reduce conflict</Term> is what a recursive,
ambiguous operator grammar produces. Declare operator precedence in a reserved
section to resolve it — earlier declarations bind more loosely:

````md
## Precedence

```gramaire precedence
%left '+' '-'
%left '*' '/'
```
````

When a build _does_ conflict, Gramaire never tells you "conflict in state 7." It
names the competing rules — "shift `+` vs reduce `Expr -> Expr + Expr`" — and it
can tell you _what kind_ of conflict it is:

- an **<Term name="lalr-artifact">LALR artifact</Term>** — canonical LR(1) or
  IELR(1) resolves it, so just build with a stronger method;
- **resolved by declaration** — your `%left`/`%right` lines already clear it, so
  the grammar compiles as written; or
- a **genuine** conflict — the grammar really is ambiguous or not LR(1) _even
  with_ the declared precedence, and needs a refactor, another precedence rule,
  or the GLR engine.

```sh
gramaire explain-conflict calc.gram.md
```

## 5. Run the recognizer

That is a complete grammar — and as it stands it is a **recognizer**: it answers
exactly one question, _does this input fit?_ Paste it into the
[Lab](/gramaire/lab) and try it (this calculator is the Lab's default):

- `12 + 3 * 4` → **accepted**
- `12 +` → **rejected** — a `Term` has to follow `+`

Try it right here — edit the grammar or the input and watch the railroad
diagrams and the verdict update live (this is the same engine the CLI runs):

<GrammarTryout grammar={CALC_RECOGNIZER} input={CALC_INPUT} />

The Lab runs the real engine — the `NUMBER` token class lexes client-side — and
re-evaluates live as you type, so you can feel the grammar accept and reject
without leaving the page. **Open in Lab ↗** on the panel above carries the
grammar straight into the full Lab.

<Aside type="tip" title="A recognizer is already useful">
  Linters, validators, and syntax highlighters often need nothing more than
  yes/no. If that is all you want, you are done. The rest of this tutorial is
  **Part 2** — turning an accepted parse into a value.
</Aside>

## 6. From recognition to a value

A recognizer throws its work away. To keep it — to build a number, or an AST —
attach a host-language **action** between `{%` and `%}`. The default action
language is **PureScript** (the core's own language):

```gramaire
Expr
  : Expr '+' Term   {% \l _ r -> Add l r %}
  | Expr '-' Term   {% \l _ r -> Sub l r %}
  | Term            {% \t -> t %}
```

Actions are **positional**: one parameter per right-hand symbol, left to right.
In `Expr '+' Term` the three parameters are the left value, the `+` token (which
we discard with `_`), and the right value.

<Aside title="From CST to AST">
  The parser first builds a <Term name="cst">concrete syntax tree</Term> — every
  token it matched, the `+` and the parentheses included. Your actions project
  that onto the <Term name="ast">abstract syntax tree</Term> you actually want:
  `\l _ r -> Add l r` keeps the two operands and drops the `+`; `'(' Expr ')'`
  returns the inner `Expr` and drops both brackets. Same recognized language,
  smaller tree.
</Aside>

If you name your fields, you can skip the lambda entirely — a **bare body** binds
the field names for you:

```gramaire
Expr
  : left:Expr '+' right:Term   {% Add left right %}
```

Gramaire rewrites that to `\left _ right -> Add left right`, so the action reads
in terms of your grammar, not positions.

<Aside title="Actions are data, backends are consumers">
  Actions are carried verbatim into the [IR](../../specs/ir-schema/); each
  backend reads only the IR. The TypeScript backend, for instance, emits a
  runnable parser and a typed Visitor over the CST without ever seeing your
  Markdown.
</Aside>

## 7. Emit a parser

At the CLI, check the file and emit artifacts from the same grammar:

```sh
# verify the file (structure, formatting, no conflicts)
gramaire fmt calc.gram.md

# emit artifacts from the same grammar
gramaire emit --backend ebnf calc.gram.md   # W3C-style EBNF
gramaire emit --backend ts   calc.gram.md   # a runnable TS parser + Visitor
gramaire emit --backend ir   calc.gram.md   # the gramaire-ir JSON
```

`gramaire fmt` also writes the railroad diagrams and the FIRST/FOLLOW table back
into the document, so the file you commit renders as complete documentation.
