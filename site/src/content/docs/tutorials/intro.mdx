Gramark's whole idea is in its name — _gram + mark_, grammar plus Markdown. A
`.grmk.md` file is a normal Markdown document that renders on GitHub — prose,
railroad diagrams, FIRST/FOLLOW tables — and is **at the same time** the exact
input the parser generator reads. Your grammar _is_ your documentation.

This tutorial builds a small calculator grammar in two passes: **Part 1** writes
a <Term name="recognizer">recognizer</Term> that decides whether input is valid,
and **Part 2** attaches _actions_ that turn a valid parse into a value. The
`gramark` CLI and the Scala core it wraps are the same code either way — there
is no separate "tutorial mode."

<Aside type="note" title="Try it with the CLI">
  This tutorial's examples are checkable today with `gramark check` and `gramark
  fmt` — build the grammar file locally as you go. An in-browser Lab (edit,
  parse, and inspect grammars live, no local install) is planned but not yet
  built; this page will link to it once it lands.
</Aside>

## 1. The shape of a `.grmk.md` file

A grammar file is a Markdown document, but **headings, prose, and images carry
no grammar semantics at all** — they're free presentation the compiler
ignores completely. The grammar itself lives entirely in fenced code blocks
tagged `gramark` (one tag, no variants), each self-identifying its role by
the shape of its own lines:

<Steps>

1. **A required `%name <name>` directive** — the grammar's name. It lives
   inside a `gramark` fence, right after the intro, with **no heading of its
   own** — the one fence role `fmt` deliberately leaves headless, since
   `%name`/`%lang` read like a source file's leading `import`/`package` line;
   there's no fallback to a heading or a file name, so a `.grmk.md` stays
   self-describing on its own.

2. **One `gramark` fence per nonterminal** — the fence's own head (`Name`
   on its own line, then `:` and its alternatives) names the rule; a `## H2`
   heading above it is just a reader-friendly label, never load-bearing.

3. **Optional `gramark` fences for tokens and precedence** — a fence whose
   every line is an ALL-CAPS `NAME : …` definition declares token classes; a
   fence whose every line is `%left`/`%right`/`%nonassoc` declares operator
   precedence. `gramark fmt`'s canonical layout groups these under
   `## Tokens` / `## Precedence` headings, but that's a formatting
   convention, not a language rule.

4. **Everything else is prose** — paragraphs, images, and headings at every
   level are free presentational grouping the compiler ignores.

</Steps>

One file is exactly one grammar: one start symbol, one namespace.

## 2. Your first rule

Create `calc.grmk.md`, name it with the required `%name` directive, and add a
first nonterminal:

````md
# Calc

A small arithmetic grammar.

```gramark
%name Calc
```

## Expr

An expression is a sum or difference of terms.

```gramark
Expr
  : Expr '+' Term
  | Expr '-' Term
  | Term
```
````

Reading the `gramark` block:

- `Expr` on its own line names the nonterminal; the `:` on the next line begins
  its alternatives.
- `|` separates alternatives — and it is the **only** separator. A line break
  inside an alternative is insignificant, so a long alternative may wrap freely.
- Quoted spellings like `'+'` (single or double quotes) are **literal
  terminals** — the exact text to match.
- A **mixed-case** name (`Expr`, `Term`) is a nonterminal; an **ALL-CAPS** name
  (`NUMBER`) is a lexer token class. A mixed-case name you never define is a
  missing rule — Gramark rejects it by name rather than treating it as a phantom
  terminal.

<Aside type="caution" title="Heads vs. fields">
  A rule head is `Name` on its own line, then `:` on the next — the line break
  is load-bearing. It is the one thing that distinguishes a head from a
  `name:Sym` **field** (written `IDENT : Sym` with no break, see §4). So never
  write a head inline as `Name : …`.
</Aside>

Add the remaining rules — `Term`, then `Factor` for numbers and parentheses:

```gramark
Term
  : Term '*' Factor
  | Term '/' Factor
  | Factor

Factor
  : '(' Expr ')'
  | NUMBER
```

`Factor` mentions the `NUMBER` token class but nothing has said what a `NUMBER`
_is_ yet. Declare token classes in a reserved `## Tokens` section, each an
ALL-CAPS name bound to a `/regex/`; mark throwaway classes (whitespace) `%skip`:

````md
## Tokens

```gramark
NUMBER : /[0-9]+/
WS     : /[ \t\r\n]+/   %skip
```
````

That is the whole recognizer's vocabulary. Gramark renders each rule as a
**railroad diagram** — the same SVGs `gramark fmt` writes back into your
`.grmk.md`, so the committed file documents itself. Here is the calculator's
shape, the stratification visible at a glance:

## 3. Surface sugar

Writing pure, left-recursive, epsilon-free productions by hand is wordy.
Gramark gives you sugar that compiles down to that clean core automatically
(`Gramark.Desugar`), so the table generator never sees a nullable rule.

<CardGrid>
  <Card title="Repetition">
    `X+` one-or-more, `X*` zero-or-more, `X?` optional. `X+` becomes a fresh
    left-recursive list; `X*` and `X?` enumerate present/absent at the use site,
    so the core stays epsilon-free.
  </Card>
  <Card title="Separated lists">
    `Comma<X>` and `Sep<X, S>` expand to one-or-more lists separated by `,` or by
    any symbol `S` — e.g. `'{' Comma<Member> '}'`.
  </Card>
  <Card title="Named fields">
    `left:Expr` names a right-hand position. The name rides onto the IR
    (`rhs[].field`) and drives generated CST accessors and visitors — without
    changing the recognized language.
  </Card>
  <Card title="Inline folding">
    `#[inline]` on a rule folds its single production into every use site, then
    drops it — a DRY tool, and a way to hand-fit a grammar into LR(1).
  </Card>
</CardGrid>

For example, a statement block is just:

```gramark
Block
  : '{' Sep<Stmt, ';'> '}'
```

## 4. Precedence and conflicts

A <Term name="shift-reduce">shift/reduce conflict</Term> is what a recursive,
ambiguous operator grammar produces. Declare operator precedence in a reserved
section to resolve it — earlier declarations bind more loosely:

````md
## Precedence

```gramark
%left '+' '-'
%left '*' '/'
```
````

When a build _does_ conflict, Gramark never tells you "conflict in state 7." It
names the competing rules — "shift `+` vs reduce `Expr -> Expr + Expr`" — and it
can tell you _what kind_ of conflict it is:

- an **<Term name="lalr-artifact">LALR artifact</Term>** — canonical LR(1) or
  IELR(1) resolves it, so just build with a stronger method;
- **resolved by declaration** — your `%left`/`%right` lines already clear it, so
  the grammar compiles as written; or
- a **genuine** conflict — the grammar really is ambiguous or not LR(1) _even
  with_ the declared precedence, and needs a refactor, another precedence rule,
  or the GLR engine.

```sh
gramark explain-conflict calc.grmk.md
```

## 5. Run the recognizer

That is a complete grammar — and as it stands it is a **recognizer**: it answers
exactly one question, _does this input fit?_ Check it with the CLI:

```sh
gramark check calc.grmk.md
```

`check` validates the grammar's own structure — no conflicts, well-formed
fences, defined nonterminals. Testing arbitrary _input_ against the grammar
interactively (`12 + 3 * 4` → accepted, `12 +` → rejected) is exactly what the
planned Lab is for; until it ships, the same table-driven parser this grammar
compiles to is exercised by the test suite and by `gramark conformance`, so a
verdict there is the same verdict the CLI would give a specific input.

<Aside type="tip" title="A recognizer is already useful">
  Linters, validators, and syntax highlighters often need nothing more than
  yes/no. If that is all you want, you are done. The rest of this tutorial is
  **Part 2** — turning an accepted parse into a value.
</Aside>

## 6. From recognition to a value

A recognizer throws its work away. To keep it — to build a number, or an AST —
attach a host-language **action** between `{%` and `%}`. Declare the action
language once, by adding `%lang` to the `%name` fence you already have from
§2:

````md
```gramark
%name Calc
%lang javascript
```
````

With `%lang javascript` declared, an action is a JS arrow function receiving one
argument — a **namedtuple** `c` — built from the alternative's right-hand
symbols:

```gramark
Expr
  : Expr '+' Term   {% (c) => ({ tag: "Add", left: c.expr, right: c.term }) %}
  | Expr '-' Term   {% (c) => ({ tag: "Sub", left: c.expr, right: c.term }) %}
  | Term
```

A position with no explicit `name:` is auto-named by its symbol — `Expr` becomes
`c.expr`, a token class lowercases the same way — but **only when that symbol
occurs once** among the rule's nameable positions. `Expr '+' Term` has two
different symbols (`Expr`, `Term`), so both auto-name cleanly; a rule with two
`Expr`s on one alternative would need explicit `name:` fields instead, since a
repeated symbol can't auto-name without colliding.

<Aside title="From CST to AST">
  The parser first builds a <Term name="cst">concrete syntax tree</Term> — every
  token it matched, the `+` and the parentheses included. Your actions project
  that onto the <Term name="ast">abstract syntax tree</Term> you actually want:
  the `Add`/`Sub` actions above keep the two operands and drop the `+`/`-`; `'('
  Expr ')'` returns the inner `Expr` and drops both brackets. Same recognized
  language, smaller tree.
</Aside>

If you'd rather name a position explicitly than rely on auto-naming — useful
when a symbol repeats, or just for readability — a `name:` field does it:

```gramark
Expr
  : left:Expr '+' right:Term   {% (c) => ({ tag: "Add", left: c.left, right: c.right }) %}
```

The field name becomes the `c` key regardless of the symbol's own name, so
`c.left`/`c.right` read in terms of your grammar, not its shape.

<Aside title="Actions are data, backends are consumers">
  Actions are carried verbatim into the [IR](../../specs/ir-schema/); each
  backend reads only the IR. The TypeScript backend, for instance, emits a
  runnable parser and a typed Visitor over the CST without ever seeing your
  Markdown.
</Aside>

## 7. Emit a parser

At the CLI, check the file and emit artifacts from the same grammar:

```sh
# verify the file (structure, formatting, no conflicts)
gramark fmt calc.grmk.md

# emit artifacts from the same grammar
gramark emit --backend ebnf calc.grmk.md   # W3C-style EBNF
gramark emit --backend ts   calc.grmk.md   # a runnable TS parser + Visitor
gramark emit --backend ir   calc.grmk.md   # the gramark-ir JSON
```

`gramark fmt` also writes the railroad diagrams and the FIRST/FOLLOW table back
into the document, so the file you commit renders as complete documentation.
